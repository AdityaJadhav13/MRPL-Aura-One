# Cross-language golden vectors

The DoseBand measurement engine is written in Dart (`packages/measurement`,
ADR-0003). The research and model-fitting work is done in Python
(`research/notebooks/`). Both compute the same optical features.

That is a hazard, and this directory is the mitigation.

## The failure this prevents

A calibration model is fitted in Python against Python-computed features, and
then applied in Dart to Dart-computed features. If the two implementations
disagree — a different percentile convention, a variance divided by `n` in one
and `n-1` in the other, a reference white rounded differently, a trimmed mean
that cuts a different number of samples — the model is applied to numbers that
are not the ones it was fitted on.

Nothing crashes. Nothing looks wrong. Every reading is biased, by a little,
permanently, and the cause is invisible by the time anybody notices.

So: **both stacks must reproduce this file, and CI fails if either does not.**

## How it works

`vectors.json` holds inputs **and** expected outputs. Each side is checked
against it independently:

| Side | Checked by |
|---|---|
| Dart | `packages/measurement/test/golden/golden_vectors_test.dart` (`dart test`) |
| Python | `python3 golden-vectors/check_parity.py` |

Because both are compared against one authoritative set of values, agreement
with the file implies agreement with each other.

```bash
# Python side
cd golden-vectors && python3 check_parity.py

# Dart side
cd packages/measurement && dart test test/golden/
```

## What is in here

| File | |
|---|---|
| `vectors.json` | Inputs, expected outputs, and the tolerances |
| `demo-badge-v0.ppm` | The shared fixture image — a rendered artificial badge |
| `doseband_reference.py` | Python implementation of the primitives |
| `check_parity.py` | Compares the Python implementation against `vectors.json` |

## Why PPM and not PNG

Both stacks have to agree on the *input pixels* before agreeing on anything
computed from them. A P6 PPM is a short ASCII header followed by raw bytes, so
a twenty-line reader in either language is provably equivalent and the
comparison starts from identical data. A PNG decoder is a dependency we would
have to trust on both sides without being able to audit either.

## Why the Python side uses no numpy

`doseband_reference.py` uses only the standard library, including its own
Jacobi eigensolver and its own Gauss-Jordan solve.

This is the point. If the Python side delegated the linear algebra to numpy and
the colour conversions to scikit-image, the two stacks might agree because both
were calling the same underlying C, and the test would stop detecting what it
exists to detect. Research notebooks should import *these* primitives and use
numpy for everything downstream of them.

## Tolerances

Both implementations use IEEE-754 doubles and the same algorithms, so the only
expected differences come from the order of floating-point operations.

| Case | Tolerance | Why |
|---|---|---|
| `scalar_absolute` | 1e-12 | Single transfer-function evaluations |
| `colour_absolute` | 1e-10 | Matrix multiply plus cube root |
| `delta_e_absolute` | 1e-10 | Long trigonometric expression |
| `homography_absolute` | 1e-8 | Iterative Jacobi eigen-decomposition |
| `statistics_absolute` | 1e-10 | Summation over thousands of samples, plus a linear solve |
| `quality_absolute` | 1e-10 | Summation over every pixel |

These are agreement tolerances between two implementations. They say nothing
about measurement accuracy, and must not be quoted as if they did.

## Provenance of the expected values

Honest statement of what this file does and does not prove.

- The expected values are **generated by the Dart engine**
  (`packages/measurement/tool/generate_golden_vectors.dart`). For most cases
  this file is therefore a **contract**, not a proof of correctness: it makes
  an unannounced divergence impossible, and that is its whole job.
- Correctness is established separately, against **independent published
  sources**, in the Dart unit tests:
  - CIEDE2000 against the 34-pair Sharma, Wu and Dalal (2005) test set —
    `test/colour/delta_e_test.dart`
  - sRGB primaries and the D65 white point against the published sRGB matrix —
    `test/colour/conversion_test.dart`
  - Percentiles against numpy's documented `linear` method —
    `test/features/statistics_test.dart`
- So: the unit tests say the arithmetic is right; these vectors say both
  languages do the same right arithmetic.

## Regenerating

```bash
cd packages/measurement && dart run tool/generate_golden_vectors.dart
```

**Regenerating changes the contract.** If any value moves, something in the
feature definition moved with it. In the same commit you must bump
`featureDefinitionVersion` in
`packages/measurement/lib/src/contract/feature_vector.dart`, so that any
calibration model fitted against the old arithmetic is refused
(`UNSUPPORTED_CALIBRATION`) rather than quietly misapplied to the new.

The Dart test asserts that the version in the file matches the version in the
code, so forgetting this is a test failure and not a silent one.

## Status of the fixture

The fixture is an **artificial demo badge** rendered under a synthetic
per-channel illuminant gain. `data_domain` in `vectors.json` is `simulated`
and carries the disclosure string verbatim.

It proves the pipeline executes and that two languages agree. It proves nothing
whatsoever about H₂S, about any chemistry, or about any real camera. The
illuminant model is a first-order per-channel gain, which is exactly the
distortion an affine correction is built to remove — so a correction passing on
this fixture has not been shown to handle a real illuminant's spectrum or
metamerism. That needs photographs of printed targets on real devices
(dossier V0).
